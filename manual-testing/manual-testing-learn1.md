# What is Software? Types of Software’s?

## Description

Software is a set of programs, instructions, and data that tells a computer how to perform tasks.

Software helps users interact with hardware and perform operations like:

* browsing
* messaging
* calculations
* gaming
* banking

Software is intangible, meaning we cannot physically touch it.

---

## Types of Software

### 1. System Software

System software manages computer hardware and provides a platform for other software.

#### Examples

* Windows
* Linux
* Android OS

#### Functions

* memory management
* hardware control
* file management

---

### 2. Application Software

Application software is created for end users to perform specific tasks.

#### Examples

* WhatsApp
* Chrome
* MS Word
* YouTube

#### Functions

* chatting
* editing
* browsing
* shopping

---

## More Information

### Characteristics of Software

* intangible
* developed using programming languages
* may contain bugs
* requires maintenance

### Software Categories Based on Platform

* Desktop Applications
* Web Applications
* Mobile Applications

---

## Example

### ATM Machine

#### Hardware

* screen
* keypad
* cash dispenser

#### Software

* ATM banking application

The software verifies:

* PIN
* account balance
* withdrawal request

and instructs hardware to dispense cash.

---

## Comparing with Others

### Software vs Hardware

| Software                  | Hardware             |
| ------------------------- | -------------------- |
| Programs and instructions | Physical components  |
| Cannot touch physically   | Can touch physically |
| Example: Chrome           | Example: Keyboard    |

---

### System Software vs Application Software

| System Software      | Application Software      |
| -------------------- | ------------------------- |
| Controls hardware    | Helps users perform tasks |
| Runs in background   | User directly interacts   |
| Mandatory for system | Optional for user         |
| Example: Windows     | Example: Instagram        |

# What is Software Testing?

## Description

Software Testing is the process of checking and verifying whether a software application works correctly according to requirements.

Testing is performed to:

* identify bugs/errors
* ensure quality
* verify functionality
* improve user experience

The main goal of testing is to deliver a defect-free and reliable product to users.

---

## More Information

### Objectives of Software Testing

* find defects
* validate requirements
* improve software quality
* reduce business risk
* ensure customer satisfaction

---

### When Testing is Done

Testing can be performed:

* during development
* after development
* before release
* after changes/updates

---

### Types of Software Testing

#### Manual Testing

Testing performed manually by testers without automation tools.

Example:

* checking login functionality manually

---

#### Automation Testing

Testing performed using tools/scripts.

Example:

* Selenium scripts for login testing

---

### What Testers Check

* functionality
* UI behavior
* performance
* security
* compatibility

---

## Example

### Login Page Testing

Tester verifies:

* valid login works
* invalid password shows error
* empty fields show validation message
* password field is masked
* login button works properly

If any issue is found, it is reported as a bug.

---

## Comparing with Others

### Testing vs Debugging

| Software Testing         | Debugging                     |
| ------------------------ | ----------------------------- |
| Finds defects            | Fixes defects                 |
| Done by testers          | Done by developers            |
| Checks software behavior | Identifies root cause in code |

---

### Manual Testing vs Automation Testing

| Manual Testing                  | Automation Testing        |
| ------------------------------- | ------------------------- |
| Human performs testing          | Tool performs testing     |
| Slower                          | Faster                    |
| Good for UI/UX                  | Good for repetitive tasks |
| Less scripting knowledge needed | Requires coding knowledge |

# Project Vs Product

## Description

Software applications are generally developed as either:

* Project
* Product

Both involve software development, but their purpose, ownership, and usage are different.

---

## Project

A project is developed for a specific client or organization based on their custom requirements.

The software is usually used only by that client.

### Characteristics

* client-specific
* fixed requirements
* fixed budget and timeline
* developed for one customer

### Examples

* Hospital Management System for one hospital
* College ERP for one university
* Banking software for a specific bank

---

## Product

A product is developed for multiple customers and released to the general market.

The same software can be used by many users or organizations.

### Characteristics

* market-based
* reusable
* developed for many customers
* continuous updates and improvements

### Examples

* WhatsApp
* Instagram
* Windows OS
* MS Office

---

## More Information

### In Project-Based Companies

The client gives requirements directly.

Development happens according to:

* client needs
* client budget
* client timeline

---

### In Product-Based Companies

Company creates software after researching market needs.

Focus areas:

* scalability
* user experience
* market competition

---

### Testing Difference

#### Project Testing

Testing mainly focuses on:

* client requirements
* business workflows

#### Product Testing

Testing mainly focuses on:

* compatibility
* scalability
* performance
* user experience

---

## Example

### Project Example

A school asks a software company to build:

* attendance system
* fee management
* student portal

This software is only for that school.

So it is a project.

---

### Product Example

Google develops Chrome browser for everyone.

Millions of users can use it.

So it is a product.

---

## Comparing with Others

### Project vs Product

| Project                  | Product                    |
| ------------------------ | -------------------------- |
| Developed for one client | Developed for many users   |
| Custom requirements      | Common market requirements |
| Limited usage            | Large-scale usage          |
| Fixed scope              | Continuous enhancements    |
| Example: School ERP      | Example: WhatsApp          |

---

### Service-Based vs Product-Based Companies

| Service-Based Company         | Product-Based Company         |

# Error, Bug & Failure

## Description

Error, Bug, and Failure are related terms in software testing, but each has a different meaning.

These terms describe different stages of a defect in software development.

---

## Error

An Error is a mistake made by a human during software development.

Errors usually occur because of:

* misunderstanding requirements
* incorrect logic
* coding mistakes

Errors are introduced by:

* developers
* testers
* analysts
* designers

---

### Example of Error

Developer writes:

```java
total = price - quantity;
```

instead of:

```java
total = price * quantity;
```

This wrong logic is an error.

---

## Bug (Defect)

A Bug is a defect present in the software because of an error.

When incorrect code is implemented into the application, it becomes a bug.

Bugs are identified during testing.

---

### Example of Bug

In shopping cart:

* total price shows incorrect amount

This issue in the application is called a bug.

---

## Failure

Failure occurs when the software does not perform expected functionality during execution.

Failures are visible to end users.

---

### Example of Failure

Application crashes during payment transaction.

This incorrect behavior is a failure.

---

## More Information

### Flow of Defect Creation

Human Mistake
↓
Error
↓
Bug in Software
↓
Failure during Execution

---

### Important Points

#### Error

* caused by humans
* happens during development

#### Bug

* exists in software/code
* identified during testing

#### Failure

* occurs when software runs incorrectly
* visible in production or testing

---

## Example

### ATM Application

#### Error

Developer writes wrong withdrawal calculation logic.

#### Bug

ATM software deducts extra amount from account.

#### Failure

Customer receives wrong balance after withdrawal.

---

## Comparing with Others

### Error vs Bug vs Failure

| Error                        | Bug                   | Failure                   |
| ---------------------------- | --------------------- | ------------------------- |
| Human mistake                | Defect in software    | Incorrect system behavior |
| Happens during coding/design | Exists in application | Happens during execution  |
| Caused by developer/tester   | Found during testing  | Seen by user/tester       |

---

### Bug vs Failure

| Bug                               | Failure                     |
| --------------------------------- | --------------------------- |
| Problem inside software           | Result of the problem       |
| May not always appear immediately | Visible during execution    |
| Internal defect                   | External incorrect behavior |

# Why the software has bugs?

## Description

Software contains bugs because software development is a human activity, and humans can make mistakes.

Bugs can occur at any stage of software development:

* requirement gathering
* design
* coding
* testing
* maintenance

Even experienced developers can introduce defects into software.

---

## More Information

### Common Reasons for Bugs

#### 1. Misunderstanding Requirements

Developers may misunderstand client requirements and implement incorrect functionality.

---

#### 2. Complex Logic

Complex business rules and calculations increase the chance of errors.

---

#### 3. Human Mistakes

Typing mistakes, logical mistakes, and incorrect assumptions can create bugs.

---

#### 4. Time Pressure

Short deadlines may cause:

* incomplete testing
* rushed coding
* skipped reviews

---

#### 5. Lack of Communication

Poor communication between:

* developers
* testers
* clients
* analysts

can lead to defects.

---

#### 6. Frequent Requirement Changes

Changing requirements during development may introduce new bugs.

---

#### 7. Incomplete Testing

If testing is insufficient, defects remain undetected.

---

#### 8. Integration Issues

Different modules may work individually but fail when combined.

---

#### 9. Environment Differences

Software may behave differently on:

* browsers
* operating systems
* devices
* networks

---

#### 10. Third-Party Dependencies

External APIs, libraries, or services may create unexpected issues.

---

### Important Observation

It is impossible to guarantee completely bug-free software for large applications.

Testing reduces bugs but cannot always eliminate all defects.

---

## Example

### E-Commerce Website

Developer implements discount calculation incorrectly.

Result:

* wrong final price shown to customers

Reason:

* misunderstanding business rule

This creates a bug in the application.

---

## Comparing with Others

### Human Error vs System Failure

| Human Error                     | System Failure                      |
| ------------------------------- | ----------------------------------- |
| Mistake during development      | Incorrect behavior during execution |
| Happens before software release | Happens while software runs         |
| Creates defects                 | Result of defects                   |

---

### Simple Application vs Complex Application

| Simple Application    | Complex Application             |
| --------------------- | ------------------------------- |
| Fewer chances of bugs | Higher chances of bugs          |
| Easier testing        | Difficult testing               |
| Smaller codebase      | Large codebase and integrations |

# Software Development Life Cycle (SDLC)

## Description

Software Development Life Cycle (SDLC) is a structured process used to develop high-quality software systematically.

SDLC defines different phases involved in software development from requirement gathering to maintenance.

The main goal of SDLC is to:

* deliver quality software
* complete development on time
* reduce cost and risk

---

## Phases of SDLC

### 1. Requirement Analysis

Business requirements are collected from the client.

#### Activities

* understand client needs
* gather functional requirements
* prepare requirement documents

---

### 2. Planning

Project planning is performed.

#### Activities

* cost estimation
* resource planning
* timeline planning
* risk analysis

---

### 3. Design

Software architecture and system design are prepared.

#### Activities

* database design
* UI design
* module design

---

### 4. Development (Coding)

Developers write source code based on design documents.

#### Activities

* coding
* unit testing
* code review

---

### 5. Testing

Testing team verifies whether software works correctly.

#### Activities

* functional testing
* regression testing
* defect reporting

---

### 6. Deployment

Software is released to production environment.

#### Activities

* installation
* configuration
* release management

---

### 7. Maintenance

After release, software is monitored and updated.

#### Activities

* bug fixing
* performance improvement
* feature enhancements

---

## More Information

### Importance of SDLC

* improves software quality
* provides clear process flow
* reduces project risk
* improves team coordination
* helps meet deadlines

---

### Different SDLC Models

* Waterfall Model
* Spiral Model
* V-Model
* Agile Model

Each model follows SDLC phases differently.

---

### Role of Tester in SDLC

Testers participate in:

* requirement analysis
* test planning
* test execution
* defect tracking

Testing is not limited to only the testing phase.

---

## Example

### Online Shopping Application

#### Requirement Phase

Client requests:

* login
* cart
* payment system

#### Design Phase

Architect designs:

* database
* UI screens
* payment flow

#### Development Phase

Developers build features.

#### Testing Phase

Testers verify:

* login works
* payment succeeds
* cart updates correctly

#### Deployment

Application released to users.

#### Maintenance

New bugs and feature updates handled.

---

## Comparing with Others

### SDLC vs STLC

| SDLC                             | STLC                                        |
| -------------------------------- | ------------------------------------------- |
| Software Development Life Cycle  | Software Testing Life Cycle                 |
| Focuses on development           | Focuses on testing                          |
| Covers complete software process | Covers testing activities only              |
| Includes coding and deployment   | Includes test execution and defect tracking |

---

### Traditional Development vs SDLC Process

| Without SDLC            | With SDLC                 |
| ----------------------- | ------------------------- |
| Unorganized development | Structured development    |
| High risk               | Better planning           |
| More defects            | Improved quality          |
| Difficult management    | Easy tracking and control |

# Waterfall Model

## Description

Waterfall Model is a traditional software development model where each phase is completed one after another in a sequential manner.

In this model:

* next phase starts only after previous phase finishes
* phases do not overlap
* process flows downward like a waterfall

It is one of the earliest SDLC models.

---

## Phases of Waterfall Model

### 1. Requirement Analysis

Requirements are gathered from the client.

---

### 2. System Design

Architecture and software design are prepared.

---

### 3. Development

Developers write the code.

---

### 4. Testing

Testing team verifies the application.

---

### 5. Deployment

Software is released to users.

---

### 6. Maintenance

Bug fixes and updates are handled after release.

---

## More Information

### Characteristics of Waterfall Model

* linear and sequential process
* documentation-oriented
* fixed requirements
* simple to understand

---

### Advantages

* easy to manage
* clear phase structure
* suitable for small projects
* good documentation

---

### Disadvantages

* difficult to change requirements later
* testing starts late
* high risk if requirements are incorrect
* not suitable for large dynamic projects

---

### When Waterfall Model is Used

* requirements are clear and fixed
* small projects
* low complexity projects

---

### Role of Testing in Waterfall Model

Testing begins only after development is completed.

Because of this:

* bugs may be found late
* fixing cost may increase

---

## Example

### College Management System

Requirements are fixed:

* student registration
* fee management
* attendance

Development happens phase by phase:

1. requirement collection
2. design
3. coding
4. testing
5. deployment

Since requirements rarely change, Waterfall Model works well.

---

## Comparing with Others

### Waterfall Model vs Agile Model

| Waterfall Model           | Agile Model                   |
| ------------------------- | ----------------------------- |
| Sequential process        | Iterative process             |
| Requirements fixed early  | Requirements can change       |
| Testing happens later     | Continuous testing            |
| Less customer involvement | Frequent customer involvement |
| Slow feedback             | Fast feedback                 |

---

### Waterfall Model vs V-Model

| Waterfall Model           | V-Model                                 |
| ------------------------- | --------------------------------------- |
| Testing after development | Testing planned parallel to development |
| Late defect detection     | Early defect detection                  |
| Simple structure          | More testing-focused                    |
| Lower testing involvement | Higher testing involvement              |

# Spiral Model

## Description

Spiral Model is a software development model that combines:

* iterative development
* risk analysis

The software is developed in multiple cycles called spirals.

Each spiral includes:

* planning
* risk analysis
* development
* testing

This model mainly focuses on reducing project risk.

---

## Phases of Spiral Model

### 1. Planning

Requirements are collected and objectives are defined.

---

### 2. Risk Analysis

Possible risks are identified and analyzed.

Examples:

* technical risks
* budget risks
* security risks

---

### 3. Engineering (Development)

Coding and development activities are performed.

---

### 4. Evaluation

Customer reviews the developed version and provides feedback.

The cycle repeats until the final product is completed.

---

## More Information

### Characteristics of Spiral Model

* iterative process
* risk-driven approach
* customer feedback after every cycle
* flexible requirement handling

---

### Advantages

* good risk management
* suitable for large projects
* supports requirement changes
* continuous customer feedback

---

### Disadvantages

* expensive model
* complex management
* requires risk analysis expertise
* not suitable for small projects

---

### When Spiral Model is Used

* large projects
* high-risk projects
* complex applications
* projects with changing requirements

---

### Role of Testing in Spiral Model

Testing happens in every spiral cycle.

Benefits:

* early defect detection
* continuous quality improvement

---

## Example

### Banking Application

A bank develops software in phases:

1. login module
2. account management
3. fund transfer
4. loan services

After each phase:

* risks are analyzed
* testing is performed
* customer feedback is collected

This reduces chances of major failures.

---

## Comparing with Others

### Spiral Model vs Waterfall Model

| Spiral Model             | Waterfall Model           |
| ------------------------ | ------------------------- |
| Iterative development    | Sequential development    |
| Focuses on risk analysis | Limited risk handling     |
| Requirements can change  | Requirements mostly fixed |
| Continuous feedback      | Feedback mainly at end    |
| More flexible            | Less flexible             |

---

### Spiral Model vs Agile Model

| Spiral Model                   | Agile Model                         |
| ------------------------------ | ----------------------------------- |
| Strong focus on risk analysis  | Strong focus on rapid delivery      |
| More documentation             | Less documentation                  |
| Suitable for high-risk systems | Suitable for fast-changing projects |
| Expensive                      | Comparatively lower cost            |

# V-Model

## Description

V-Model (Verification and Validation Model) is an SDLC model where testing activities are planned and performed parallel to development activities.

It is an extension of the Waterfall Model.

In V-Model:

* every development phase has a corresponding testing phase
* testing starts early
* defects are identified earlier

The structure looks like the letter “V”.

---

## Structure of V-Model

### Verification Side (Left Side)

Focuses on development activities.

#### Phases

1. Requirement Analysis
2. System Design
3. High-Level Design
4. Low-Level Design
5. Coding

---

### Validation Side (Right Side)

Focuses on testing activities.

#### Corresponding Testing Phases

| Development Phase    | Testing Phase       |
| -------------------- | ------------------- |
| Requirement Analysis | Acceptance Testing  |
| System Design        | System Testing      |
| High-Level Design    | Integration Testing |
| Low-Level Design     | Unit Testing        |

---

## More Information

### Verification

Verification checks:
“Are we building the product correctly?”

Focus:

* reviews
* walkthroughs
* inspections

No code execution required.

---

### Validation

Validation checks:
“Are we building the correct product?”

Focus:

* executing software
* testing functionality

---

### Characteristics of V-Model

* testing starts early
* structured approach
* strong quality focus
* better defect prevention

---

### Advantages

* early defect detection
* better test planning
* improved quality
* easy to manage

---

### Disadvantages

* less flexible for requirement changes
* expensive for frequent modifications
* not suitable for highly dynamic projects

---

### When V-Model is Used

* stable requirements
* medium-sized projects
* quality-critical applications

Examples:

* banking systems
* healthcare software
* embedded systems

---

## Example

### ATM Application

#### Requirement Phase

Client defines:

* withdrawal
* balance check
* mini statement

#### Testing Planning

Acceptance test cases prepared during requirement phase.

#### Development

Developers build ATM modules.

#### Testing

* unit testing for functions
* integration testing for modules
* system testing for complete ATM flow

This helps identify issues early.

---

## Comparing with Others

### V-Model vs Waterfall Model

| V-Model                              | Waterfall Model                  |
| ------------------------------------ | -------------------------------- |
| Testing planned early                | Testing starts after development |
| Better defect detection              | Defects found later              |
| Verification and validation included | Mainly sequential flow           |
| Higher quality focus                 | Lower testing involvement        |

---

### Verification vs Validation

| Verification        | Validation                    |
| ------------------- | ----------------------------- |
| Checks process      | Checks product                |
| Static activity     | Dynamic activity              |
| No code execution   | Requires code execution       |
| Finds defects early | Ensures correct functionality |

# Static Testing & Dynamic Testing

## Description

Static Testing and Dynamic Testing are two important software testing approaches.

They differ based on whether the software code is executed or not during testing.

---

## Static Testing

Static Testing is a testing method where software is evaluated without executing the code.

It mainly checks:

* documents
* design
* source code
* requirements

The purpose is to identify defects early before execution.

---

### More Information about Static Testing

#### Techniques Used

* reviews
* walkthroughs
* inspections
* code analysis

---

#### Characteristics

* no code execution
* performed early in SDLC
* helps prevent defects
* low cost defect detection

---

#### Advantages

* early bug detection
* reduces development cost
* improves code quality
* saves testing time later

---

#### Example

Reviewing requirement documents and identifying missing requirements before development starts.

Another example:
Developer reviews code manually and finds logical mistakes.

---

## Dynamic Testing

Dynamic Testing is a testing method where software is executed to validate actual behavior.

It checks:

* functionality
* performance
* output
* runtime behavior

---

### More Information about Dynamic Testing

#### Techniques Used

* functional testing
* regression testing
* system testing
* performance testing

---

#### Characteristics

* requires code execution
* validates actual software behavior
* identifies runtime defects

---

#### Advantages

* checks real application behavior
* verifies expected output
* identifies runtime failures

---

#### Example

Testing login functionality by entering username and password.

If login fails unexpectedly, defect is identified during dynamic testing.

---

## Example

### E-Commerce Application

#### Static Testing

Tester reviews:

* requirement document
* UI design
* code logic

without running the application.

---

#### Dynamic Testing

Tester:

* opens application
* adds items to cart
* performs payment

to verify actual behavior.

---

## Comparing with Others

### Static Testing vs Dynamic Testing

| Static Testing        | Dynamic Testing             |
| --------------------- | --------------------------- |
| No code execution     | Code execution required     |
| Finds defects early   | Finds runtime defects       |
| Checks documents/code | Checks application behavior |
| Lower cost            | Higher execution effort     |
| Preventive approach   | Corrective approach         |

---

### Verification vs Validation

| Verification                  | Validation                    |
| ----------------------------- | ----------------------------- |
| Related to static testing     | Related to dynamic testing    |
| Checks correctness of process | Checks correctness of product |
| No software execution         | Requires software execution   |

# Verification & Validation

## Description

Verification and Validation are two important quality assurance activities in software testing.

They ensure:

* software is developed correctly
* software meets customer requirements

Both help improve software quality but focus on different aspects.

---

## Verification

Verification checks whether the software is being developed correctly according to specifications and design documents.

It answers:

> “Are we building the product correctly?”

Verification is a static process.

---

### More Information about Verification

#### Activities

* reviews
* walkthroughs
* inspections
* document checking

---

#### Characteristics

* no code execution
* performed early in development
* focuses on process and documents

---

#### Advantages

* early defect detection
* reduces development cost
* improves development quality

---

#### Example

Reviewing requirement documents to ensure all business requirements are included correctly.

---

## Validation

Validation checks whether the developed software satisfies customer requirements and works correctly.

It answers:

> “Are we building the correct product?”

Validation is a dynamic process.

---

### More Information about Validation

#### Activities

* executing software
* functional testing
* system testing
* user acceptance testing

---

#### Characteristics

* code execution required
* focuses on actual software behavior
* validates final product

---

#### Advantages

* ensures software meets user expectations
* identifies runtime issues
* improves customer satisfaction

---

#### Example

Testing login functionality by entering valid and invalid credentials.

---

## Example

### Food Delivery Application

#### Verification

Checking requirement document:

* restaurant search
* online payment
* order tracking

to ensure requirements are correctly documented.

---

#### Validation

Executing the application to verify:

* orders are placed successfully
* payment works correctly
* tracking updates properly

---

## Comparing with Others

# Cookies & Sessions

## Description

Cookies and Sessions are mechanisms used by web applications to store and manage user information during interactions with a website.

They help applications:

* maintain user state
* manage login information
* track user activity
* improve user experience

---

## Cookies

Cookies are small text files stored in the user's browser by a website.

They store information such as:

* login details
* user preferences
* session identifiers

Cookies remain on the client side.

---

## More Information about Cookies

### Types of Cookies

#### Session Cookies

Temporary cookies deleted after browser closes.

---

#### Persistent Cookies

Stored for a longer duration until expiry.

---

#### Secure Cookies

Used only over HTTPS connections.

---

### Common Uses

* remember login
* save language settings
* track user activity
* store shopping cart items

---

### Advantages

* improves user experience
* faster user access
* personalized settings

---

### Disadvantages

* security/privacy risks
* can be modified by users

---

## Sessions

A Session is a server-side mechanism used to store user data temporarily during interaction with the application.

Each user gets a unique session ID.

Session data is stored on the server.

---

## More Information about Sessions

### Characteristics

* server-side storage
* more secure than cookies
* temporary in nature

---

### Common Uses

* user authentication
* maintaining login state
* secure transaction handling

---

### Session Expiry

Session automatically ends after:

* logout
* inactivity timeout
* browser close (sometimes)

---

### Advantages

* more secure
* sensitive data not stored in browser

---

### Disadvantages

* server memory usage
* session timeout may affect users

---

## Example

### Online Shopping Website

#### Cookies

Website stores:

* preferred language
* recently viewed items

in browser cookies.

---

#### Sessions

After login:

* user authentication details
* cart information

stored in session on server.

---

## Real-Time Example

### Banking Application

Session maintains:

* logged-in user identity
* transaction state

Cookies may store:

* theme preference
* language settings

Sensitive data should not be stored in cookies.

---

## Comparing with Others

### Cookies vs Sessions

| Cookies                         | Sessions                |
| ------------------------------- | ----------------------- |
| Stored in browser               | Stored on server        |
| Less secure                     | More secure             |
| Can persist after browser close | Usually temporary       |
| Small storage capacity          | Larger storage possible |
| Client-side storage             | Server-side storage     |

---

### Session Cookie vs Persistent Cookie

| Session Cookie               | Persistent Cookie          |
| ---------------------------- | -------------------------- |
| Temporary                    | Stored long-term           |
| Deleted after browser closes | Remains until expiry       |
| Used for active sessions     | Used for remembering users |

# Test Case Design Techniques

## Description

Test Case Design Techniques are systematic methods used to create effective test cases that provide maximum test coverage with minimum effort.

These techniques help testers:

* identify important test scenarios
* reduce redundant test cases
* improve testing efficiency

They are mainly used in:

* functional testing
* validation testing
* black box testing

---

## 1. Equivalence Class Partitioning (ECP)

### Description

Equivalence Class Partitioning divides input data into groups called equivalence classes.

Each group behaves similarly, so testing one value from each group is usually enough.

---

### More Information

#### Purpose

* reduce number of test cases
* improve test coverage efficiently

---

#### Types

* valid equivalence class
* invalid equivalence class

---

### Example

Age field accepts:

```text id="3yr4ax"
18 to 60
```

#### Valid Class

* 18–60

#### Invalid Classes

* below 18
* above 60

Test values:

```text id="q4e1dt"
20, 10, 70
```

---

## 2. Boundary Value Analysis (BVA)

### Description

Boundary Value Analysis focuses on testing values at the boundaries because defects commonly occur near limits.

---

### More Information

#### Boundary Values

* minimum value
* maximum value
* values just below and above boundaries

---

### Example

Allowed age:

```text id="fjg5m1"
18 to 60
```

Test values:

```text id="vm1h0w"
17, 18, 19, 59, 60, 61
```

---

## 3. Decision Table Testing

### Description

Decision Table Testing is used when application behavior depends on multiple conditions and combinations.

A table is created with:

* conditions
* actions/results

---

### More Information

#### Purpose

* test business rules systematically
* handle complex combinations

---

### Example

ATM withdrawal allowed only if:

* correct PIN
* sufficient balance

| PIN Correct | Balance Available | Result               |
| ----------- | ----------------- | -------------------- |
| Yes         | Yes               | Withdrawal Success   |
| Yes         | No                | Insufficient Balance |
| No          | Yes               | Invalid PIN          |
| No          | No                | Transaction Failed   |

---

## 4. State Transition Testing

### Description

State Transition Testing verifies application behavior when moving from one state to another based on events/actions.

---

### More Information

#### Purpose

* validate state-based behavior
* verify transitions between states

---

### Example

Login system:

* active state
* locked state

After 3 wrong passwords:

```text id="gk4q9d"
Account Locked
```

---

## 5. Error Guessing

### Description

Error Guessing is an experience-based testing technique where testers predict possible defects based on past experience and intuition.

---

### More Information

#### Purpose

* identify hidden defects
* test risky areas quickly

---

### Common Guessing Areas

* empty fields
* special characters
* invalid dates
* divide by zero

---

### Example

Tester guesses user may:

* submit form without entering data
* upload invalid file format

and tests those scenarios.

---

## Comparing with Others

### ECP vs BVA

| ECP                       | BVA                            |
| ------------------------- | ------------------------------ |
| Divides input into groups | Focuses on boundary values     |
| Reduces test cases        | Finds boundary-related defects |
| Group-based testing       | Limit-based testing            |

---

### Decision Table vs State Transition

| Decision Table Testing        | State Transition Testing  |
| ----------------------------- | ------------------------- |
| Condition combination-focused | State change-focused      |
| Business rule validation      | Workflow/state validation |
| Table-driven testing          | State behavior testing    |

Combination of forward and backward traceability.

# Defect/Bug Life Cycle

## Description

Defect Life Cycle (Bug Life Cycle) is the process through which a defect moves from identification to closure during software testing.

It defines different stages/statuses of a defect and helps teams track defect progress systematically.

---

## More Information

### Purpose of Defect Life Cycle

* track defect status
* manage defect fixing process
* improve communication between testers and developers
* ensure defects are resolved properly

---

## Stages of Defect Life Cycle

### 1. New

Tester identifies defect and reports it.

Status:

```text id="v4m2rq"
New
```

---

### 2. Assigned

Defect is assigned to a developer for fixing.

Status:

```text id="d1k9zx"
Assigned
```

---

### 3. Open

Developer analyzes defect and starts fixing it.

Status:

```text id="n7p5lw"
Open
```

---

### 4. Fixed

Developer fixes defect and provides updated build.

Status:

```text id="q8s4ye"
Fixed
```

---

### 5. Retest

Tester retests defect using updated build.

Status:

```text id="w0r6tn"
Retest
```

---

Tester confirms defect is fixed successfully.

Status:

```text id="b5y2kv"
Verified
```

---

Defect is closed after successful verification.

Status:

```text id="x3m7cd"
Closed
```

### Rejected

* not reproducible
* works as expected

Same defect already reported earlier.

---

## More Information

### Purpose of Testing Metrics

* measure testing progress
* evaluate product quality
* identify process improvement areas
* support project reporting

---

## Types of Testing Metrics

### 1. Process Metrics

Measure testing process efficiency.

Examples:

* test execution progress
* defect fixing rate

---

### 2. Product Metrics

Measure software quality.

Examples:

* defect density
* defect leakage

---

### 3. Project Metrics

Measure overall project performance.

Examples:

* testing effort
* cost estimation
* schedule variance

---

## Common Software Testing Metrics

### Test Case Execution Percentage

Formula:

\text{Execution Percentage} = \frac{\text{Executed Test Cases}}{\text{Total Test Cases}} \times 100

Measures how many test cases are executed.

---

### Defect Density

Formula:

\text{Defect Density} = \frac{\text{Number of Defects}}{\text{Size of Software}}

Measures defects relative to software size.

---

### Defect Leakage

Formula:

\text{Defect Leakage} = \frac{\text{Defects Found After Release}}{\text{Total Defects}} \times 100

Measures defects missed during testing.

---

### Test Coverage

Measures percentage of requirements/features tested.

---

### Pass Percentage

Formula:

\text{Pass Percentage} = \frac{\text{Passed Test Cases}}{\text{Executed Test Cases}} \times 100

Measures successful test execution rate.

---

* quality evaluation

---

## Advantages

* identifies quality trends
* supports project management

---

## Disadvantages

# Principles of Software Testing

## Description

Principles of Software Testing are fundamental guidelines that help testers perform effective and efficient testing.

These principles explain:

* how testing should be approached
* limitations of testing
* best practices for finding defects

Understanding these principles improves software quality and testing strategy.

---

## More Information

## 1. Testing Shows Presence of Defects

### Description

Testing can show that defects exist, but it cannot prove that software is completely defect-free.

Even if no bugs are found, some hidden defects may still exist.

---

### Example

Application works correctly during testing but crashes later under heavy user load.

---

## 2. Exhaustive Testing is Impossible

### Description

Testing every possible input, condition, and scenario is impossible for most applications.

Therefore, testers prioritize important test cases.

---

### Example

A login field with millions of possible combinations cannot be tested completely.

---

## 3. Early Testing Saves Time and Cost

### Description

Defects identified in early stages are cheaper and easier to fix.

Late defect detection increases fixing cost and project risk.

---

### Example

Requirement issue found before coding is easier to fix than after deployment.

---

## 4. Defect Clustering

### Description

A small number of modules usually contain most defects.

This is also called:

```text id="q1x8lv"
80/20 Rule
```

meaning:

* 80% defects found in 20% modules.

---

### Example

Payment module contains majority of project defects.

---

## 5. Pesticide Paradox

### Description

Repeating the same test cases again and again eventually stops finding new defects.

Test cases should be reviewed and updated regularly.

---

### Example

Regression suite repeatedly executed but new defects remain undetected because tests never changed.

---

## 6. Testing Depends on Context

### Description

Testing approach differs depending on:

* application type
* business domain
* project risk

No single testing method works for all projects.

---

### Example

Banking application requires stronger security testing than a gaming app.

---

## 7. Absence of Errors Fallacy

### Description

Even if software has very few defects, it is useless if it does not satisfy user requirements.

Quality means:

* correct functionality
* useful functionality

---

### Example

Application works perfectly technically but missing important business feature.

---

## Characteristics of Testing Principles

* guide testing strategy
* improve testing effectiveness
* help manage testing limitations

---

## Advantages

* improves testing efficiency
* helps prioritize testing effort
* reduces project risk

---

## Disadvantages

* principles require practical understanding
* cannot guarantee defect-free software

---

## Real-Time Example

### Banking Application

Testing focuses heavily on:

* security
* transactions
* performance

because testing depends on application risk and business impact.

---

## Comparing with Others

### Early Testing vs Late Testing

| Early Testing            | Late Testing                |
| ------------------------ | --------------------------- |
| Lower fixing cost        | Higher fixing cost          |
| Easier defect correction | Difficult defect correction |
| Reduces project risk     | Increases project risk      |

---

### Exhaustive Testing vs Risk-Based Testing

| Exhaustive Testing      | Risk-Based Testing              |
| ----------------------- | ------------------------------- |
| Tests all possibilities | Tests important/high-risk areas |
| Mostly impossible       | Practical approach              |
| Very high effort        | Efficient testing strategy      |
